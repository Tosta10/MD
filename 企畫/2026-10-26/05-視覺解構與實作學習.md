# 視覺解構、實作與學習

狀態：功能研究及設計提案。現有插件主要保存圖片及比較紀錄，尚沒有本文件所述的完整流程。

## 1. 成果目標

讓 AI 不只描述「這是一張藍色科技介面」，而能回答：

- 哪些視覺結構造成這種效果？哪些是觀察、哪些只是猜測？
- 在目前技術棧中，可以用什麼布局、材質、渲染與互動方式實現？
- 哪些參數會影響效果，代價是什麼？
- 實際產出與參考差在哪裡，哪些差異值得修正？
- 下次相似任務應該重用哪個方法、避開哪個失敗？

產品不承諾從圖片還原原作者的精確原始碼。相同畫面可能有多種實現方式，單張截圖也不能證明動態、互動、響應式或效能行為。

## 2. 一份視覺資料的組成

| 物件 | 必要內容 | 為什麼不只用 MD |
|---|---|---|
| Asset | 原圖／影片、hash、尺寸、格式、來源、使用權、擷取環境 | 保留視覺證據，不用文字取代圖片 |
| Observation | 可見元素、文字、層級、量測、未知項 | 區分觀察與推論 |
| Region | 區域框、父子層級、標籤、對應元素 | 針對局部載入、比較與修正 |
| State／Timeline | 狀態、觸發、時間戳、轉場與運動 | 動態不能只靠一張圖描述 |
| VisualRecipe | 適用場景、技術、參數、前提、陷阱、驗證 | 把實現方法做成可檢索知識 |
| Implementation | 程式／場景／資源版本、最小範例、環境 | 可以重現，減少描述歧義 |
| Evaluation | 對照圖、量測、人工偏好、問題定位 | 分辨「看起來像」與「有用」 |
| Lesson | 成功條件、失敗原因、可重用範圍 | 沉澱精簡方法，不複製整段對話 |

所有資料都連到相同的穩定 ID 與版本。圖片／影片保存於受控資產目錄，資料庫保存中繼資料；MD 是可讀匯出或方法附件，不承擔所有媒體與索引。

Asset 增加檔案 hash 去重、像素尺寸、色彩空間、來源日期、viewport、DPR、瀏覽器／引擎版本、字型與資源版本。相同圖片不同擷取條件可共用二進位，但保留不同觀察紀錄。

## 3. 靜態畫面如何解構

按工作需要選擇觀察層，不強制每張圖片輸出巨大報告。

| 層面 | 要提取的事 | 對應實現方向 |
|---|---|---|
| 任務與資訊 | 主次目標、閱讀順序、視覺焦點 | 資訊架構、元件責任、內容優先序 |
| 幾何與布局 | 欄位、對齊、間距、尺寸比例、重疊 | Grid／Flex／定位、引擎容器與錨點 |
| 字體與圖示 | 字重、大小、行距、字形、基線 | 字型資源、排版 token、圖示系統 |
| 顏色與對比 | 背景、前景、強調、材質變化 | 色彩 token、狀態與可及性規範 |
| 表面效果 | 邊框、陰影、模糊、漸層、噪點、遮罩 | CSS／SVG／Canvas／shader 分層 |
| 光影與空間 | 光源、投影、深度、透視、反射 | 2D 合成或 3D 場景、材質與燈光 |
| 資產 | 圖片、紋理、模型、字型、授權 | 可用素材清單與替代策略 |
| 隱含狀態 | 選取、hover、停用、載入、錯誤 | 狀態機假設；需額外觀察驗證 |
| 響應式 | 可見斷點線索與內容伸縮 | 多尺寸實驗；單圖不推定全部規則 |

區域座標以原圖像素及正規化比例共同記錄，避免縮圖後標記錯位。OCR 文字是可校正的觀察，不自動當成準確規格。若能取得 DOM、computed styles、accessibility tree 或引擎場景資料，優先拿來補足布局與語義；不能把不可取得的資料假裝已讀到。

同一效果至少分成：

1. 可觀察結果：例如邊緣有柔和光線、背景細節被模糊。
2. 實作假設：可能是背景模糊、半透明覆蓋或預先處理圖片。
3. 最小實驗：用兩種方式在目標環境測試。
4. 成果證據：截圖、運作條件及效能差異。

視覺模型可能誤讀小字、精確空間關係與細節，因此原圖、局部裁切及程式量測需互相補充。[OpenAI Images and Vision](https://developers.openai.com/api/docs/guides/images-vision)

## 4. 動態畫面與互動

第一階段可支援明確界定的影片格式、GIF 或連續截圖，經格式與尺寸／時長限制後在本機解碼。先建立接觸表及狀態索引，AI 再按需讀取少量原始影格；不要把完整影片每一影格都送入模型。

時間軸包含：

- 起始狀態、觸發方式、結束狀態、可否中斷、反向或重複。
- 元素位置、縮放、旋轉、透明度、模糊或材質隨時間的變化。
- 動畫時間、延遲、緩動曲線的估計及證據範圍。
- 物件運動、攝影機運動與畫面剪接分開。
- 使用者輸入、焦點／選取、載入及資料變化的因果順序。
- frame pacing、掉幀、輸入回應及減少動態模式。

例如一個展開面板的影片，可以觀察容器尺寸和內容透明度分別變化，但不能只憑影片斷言原作者使用某個動畫函式庫。插件應輸出可替代的實作方案，並以目標裝置的實測選擇。

從靜態圖建立動態原型時，明確標為新設計，不能記成參考作品原有行為。

## 5. 效果配方與可執行範例

VisualRecipe 的入口短而聚焦，詳細資料作附件：

~~~text
recipe/
  index.json               用途、適用環境、版本、來源、驗證
  overview.md              一段效果說明、關鍵參數、選用理由
  references/              區域描述、來源定位、觀察與限制
  implementations/         依技術棧分開的最小範例
  evaluations/             基準畫面、行為／效能結果、改進紀錄
~~~

此為概念結構，實際可以由資料庫管理並按需匯出，不要求每筆資料都建立實體資料夾。

每個實作變體記錄：

| 欄位 | 示例用途 |
|---|---|
| stack、version、environment | HTML/CSS 或 Godot，版本與渲染器 |
| prerequisites | 字型、紋理、插件、裝置能力 |
| rendering_layers | 背景、模糊、面板、邊緣、內容的順序 |
| parameters | 間距、透明度、模糊半徑、動畫時長等及可調範圍 |
| tradeoffs | 效能、可讀性、相容性、易維護程度 |
| gotchas | 溢出、遮罩邊界、合成層、色彩空間等特定問題 |
| verification | 尺寸、狀態、效能及驗收方法 |
| source_refs | 來源與實驗證據 |
| example_ref | 可重現程式／場景的版本與 hash |

Web UI、Canvas／WebGL、遊戲引擎需要不同實作適配器；不要把 CSS 配方直接當成 Godot 場景方法。新框架可以新增適配器及範例，但必須說明是否真的執行驗證。

外部範例程式視為未信任輸入。下載、解壓、執行與網路存取分開授權，限定輸出目錄和資源上限；不能讓「學習素材」自動取得全部本機權限。

## 6. 實現與評價閉環

~~~mermaid
flowchart LR
  A[參考與目標] --> B[區域／狀態解構]
  B --> C[實作假設與最小範例]
  C --> D[目標環境呈現]
  D --> E[條件對齊與比較]
  E --> F{驗收}
  F -->|需改善| C
  F -->|達標或到達資源上限| G[成果與限制回報]
  G --> H[提取有證據的可重用方法]
~~~

設定明確修正次數、時間及 token 上限；達到上限時回報已完成與剩餘問題，不能用無限循環代替品質判斷。

比較前對齊 viewport、DPR、字型、素材版本、內容、瀏覽器／引擎與動畫狀態。對動態不穩定區域應固定狀態或使用時間段評價；遮蔽區域必須標示，不能把主要缺陷遮住後宣稱通過。[Playwright Visual Comparisons](https://playwright.dev/docs/test-snapshots)

評價維度：

| 維度 | 證據 | 不應推論 |
|---|---|---|
| 內容完整 | OCR／DOM／場景元素對照 | 文字存在不代表資訊易讀 |
| 布局與幾何 | 區域、邊界、間距、對齊差異 | 像素接近不代表可維護 |
| 視覺相似 | 差異圖、選用 SSIM／感知指標 | 單一分數不等於審美 |
| 功能與互動 | 可操作行為及狀態驗證 | 截圖不能證明按鈕有用 |
| 可讀性 | 對比、縮放、文字溢出、鍵盤操作 | 高對比不能代替整體易用性 |
| 動態品質 | 時序、軌跡、輸入回應、掉幀 | 平均 FPS 不能代表全程流暢 |
| 審美與目標吻合 | 明確 rubric、盲測配對、人類偏好 | 模型自評高分不是客觀結論 |
| 資源成本 | 記憶體、CPU/GPU、載入與渲染 | 測試機通過不等於所有裝置通過 |

審美 rubric 使用可討論標準，例如層級清楚、比例一致、密度適合任務、風格與參考相符；以使用者選定的例子校準。保留多維結果，避免一個總分掩蓋「相似但不能操作」的問題。

Design2Code 研究支持把截圖到程式的評價拆成布局、元素等面向並配合人工判斷；它不證明本插件會提升，也不是遊戲或動態畫面的通用評分器。[Design2Code](https://arxiv.org/abs/2403.03163)

## 7. 學習回報與重新使用

每次成果回報固定包含：

1. 本次欲重現的效果及適用環境。
2. 採用的參考、知識與實作方案，及關鍵取捨。
3. 實際產物與可重現條件。
4. 已驗證項目、未達標項目與證據。
5. 最值得改善的 1–3 項，按影響與修正成本排序。
6. 新增或修訂的可重用方法，以及仍屬假設的部分。
7. 本次研究、實作、驗證各自的用量與時間。

驗證者可使用獨立上下文或不同評估途徑，但是否啟用其他代理由宿主能力與使用者授權決定。插件本身不能假設能任意建立多代理或自動得到客觀判斷。

重新使用時，先載入效果配方入口及驗證摘要。只有需要重現細節時才讀原圖區域、時間片段或程式；完整原始媒體仍保留在本機。失敗案例保存「何種條件下失敗、如何辨識、避免方式」，不把一次失敗泛化成永遠禁止。

## 8. 分段落地

- P0 先補 AI 匯入契約與讀取預算，P1 統一素材中繼資料、作用範圍、來源與 hash。
- P2a 加入區域標記、結構描述、靜態配方、對齊截圖及比較回報。
- P2b 加入時間軸、關鍵影格、狀態機與動態評價。
- P2c 依實際需求加入特定 Web／引擎執行與量測適配器。
- 未通過相同預算下的品質比較前，進階模型分析、影片與多輪評審維持選用。

每階段都應能獨立產生有用成果，不能先囤大量圖片與自動描述，卻沒有可檢索的方法或實作驗證。
