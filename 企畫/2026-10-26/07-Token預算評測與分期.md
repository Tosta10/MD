# Token 預算、成效評測與開發分期

狀態：規劃及待驗證門檻。沒有實作本企畫功能，也沒有重新執行產品測試或 AI 品質實驗。本文件不提供未量測的提升百分比或固定費用承諾。

## 1. 現在的消耗盲點

目前知識工具有欄位分頁、回傳 bytes 限制與可選 runId 帳本，這些措施有價值，但不能等同完整 token 控制：

- 48 KiB 的知識帳本不是全部模型上下文預算；其他讀取、圖片、工具 schema、歷史與輸出可能另有消耗。
- UTF-8 bytes / 2 只是估計。中英文、JSON、程式碼及模型 tokenizer 的差異不能由同一比例準確涵蓋。
- 相同內容即使只讀一次，仍可能在後續模型呼叫的歷史中重複出現；工具回傳去重不等於整段對話零重複計費。
- 圖片檔案小，不代表視覺 token 一定少。縮圖、detail、分辨率與所用模型會改變成本。
- 背景摘要、embedding、重新排序、反覆評審及失敗重試，可能比最後交付的脈絡包更貴。
- 工具定義也占空間；宿主是否延後載入、快取或重送，插件不能自行假設。

本次只讀取工具定義並以 JSON UTF-8 bytes 計算：MD 23 個工具約 12,251 bytes，理解工作台 27 個約 21,090 bytes；按名稱去重合計 45 個、約 31,434 bytes。這不是實際 token 或帳單，也不表示所有宿主每次都載入全部。它指出值得量測與改善的 schema 重複，而非已證明的浪費量。

## 2. 分層預算

以下是建議初始產品預設，需按模型上下文大小與任務效果調整。文字數值指插件額外提供的唯一材料估計，不包含使用者原始需求、宿主系統提示、既有歷史、推理、模型輸出及其他工具。

| 任務 | 額外文字材料 | 媒體策略 | 運作方式 |
|---|---:|---|---|
| 明確的小修改 | 0–800 tokens | 預設不讀媒體 | 可完全跳過知識檢索 |
| 一般實作／文件整理 | 約 1,500–3,000 tokens | 有需要才讀 | 3–6 摘要，按需 1–2 詳細片段 |
| 跨領域或複雜規劃 | 約 3,000–6,000 tokens | 明列預算 | 分階段讀取，不先讀全部 |
| 視覺分析／實作 | 約 4,000–8,000 文字 tokens | 先 1 張總覽＋最多 2 張必要區域 | 圖像另估算並計入總上限 |
| 動態分析 | 約 4,000–8,000 文字 tokens | 先接觸表，再最多 4 張必要影格 | 只在缺失會影響判斷時增加 |
| 大量整理 | 不直接按檔案數增加單次上下文 | 通常不讀媒體 | 分批候選、服務端計算、摘要回傳 |

圖片與影片不能用固定每張 token 數推算所有模型。優先使用宿主實際用量；不可得時顯示模型相關估計與保守上界，且標為估計。[OpenAI Images and Vision](https://developers.openai.com/api/docs/guides/images-vision)

預算有三層：單次回應上限、整個 run 累計上限、選用外部模型／儲存費用上限。快到上限時先停止低價值擴充、給出目前證據與剩餘缺口；需要提高上限時依既有授權處理，不能偷偷開新 run 規避。

## 3. 合理壓縮的順序

優先順序是「不讀無關資料 → 查準 → 讀小範圍 → 結構化 → 去重 → 必要才摘要」。

| 方法 | 節省來源 | 保留條件 |
|---|---|---|
| 任務／環境硬篩選 | 無關領域不入候選 | 不用猜測環境排除可能適用資料 |
| 短入口＋附件 | 不每次讀完整方法 | 入口保留觸發、前提、例外與定位 |
| 欄位／段落／區域讀取 | 只取得有用部分 | 跨段依賴與否定條件一起載入 |
| 增量分析與內容 hash | 不重複處理未變更資料 | parser／規則／模型改變也要失效 |
| 版本去重及差異回傳 | 同一 run 不重送未變內容 | 任務或資料版本改變後可重新讀取 |
| 工具回應精簡 | 移除冗長預設值與重複包裝 | 保留狀態、範圍、來源、錯誤及下一步 |
| 語意摘要 | 濃縮真正需要的長材料 | 保留不可丟失的限制，能回到原文 |
| 視覺分層 | 不每次重讀全圖／全部影格 | 保留總覽與比例，必要時看原圖 |
| 宿主 prompt cache | 降低部分重複輸入費用／延遲 | 不把快取當成上下文縮短 |

不能刪掉的內容：使用者限制、否定條款、適用版本、數值與單位、重要例外、來源定位、未確認假設。摘要應保存這些條款的覆蓋檢查，不能反覆摘要上一份摘要而逐步失真。

壓縮 zip／gzip 檔案不會直接減少模型需要理解的資訊；如果只是把壓縮內容交給模型，通常沒有益處。應在本機解碼、搜尋與選取後才送入模型。不要為了短而創造大量無法理解的縮寫或刪掉語意標籤。

上下文工程關注的是每次提供哪些高價值資訊，並非把所有資料寫成更長提示詞。[Anthropic Context Engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

## 4. 一個透明的估算例子

假設 500 份經驗，每份已用目標 tokenizer 量得平均 500 tokens：

- 全部載入為 250,000 tokens。
- 一次任務可改成：任務摘要 500＋方法入口 200＋6 份摘要各 80＋2 份細節各 650＋必要例外 300＝2,780 tokens。
- 唯一材料量相對少約 98.9%。

這只是說明「不全讀」的上限差異，不是本插件實測節省率；也沒有包含工具定義、媒體、研究、產生摘要的成本或後續呼叫。正確比較應對目前版本與候選方案實測，不能用「每次讀完全部資料」這個過差基線宣傳成效。

## 5. 真正費用怎麼算

單次任務總成本應累加所有呼叫：

~~~text
總成本 =
  Σ(未快取輸入 tokens × 輸入費率
   + 快取輸入 tokens × 快取費率
   + 可適用的快取寫入成本
   + 計費輸出 tokens × 輸出費率)
  + embedding 費用
  + reranker／其他模型費用
  + 檢索與儲存費用
~~~

影像若已計入輸入 tokens，不重複計費；推理 token 依供應商回報與計價方式計入，不能只看畫面上顯示的回答字數。用量未提供時回報未知或估計，不能當作零。

Prompt cache 通常需要相符的前綴與模型／宿主條件；它可能降低費用和延遲，卻不減少實際上下文長度。整理過度頻繁也可能打破快取，必須比較「縮短後總費用」與「保留快取前綴的總費用」，不能只看字數。[OpenAI Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching)

Codex 訂閱、API 與其他 AI 宿主的成本呈現不同。插件最多保存自己可觀察的用量並接收宿主回報，不保證能換算使用者訂閱額度；本企畫不假設固定模型價格。

維護是否划算也可量測：若一次整理成本為 C，每個後續任務平均節省 S，則要超過 C/S 次重用才回本；S 必須是實測正值，且品質不下降。只會用一次的資料通常不值得投入昂貴摘要與向量化。

## 6. 如何證明對 AI 有實質提升

三組條件：

| 組別 | 條件 |
|---|---|
| A | 相同 AI 與可存取來源，使用一般檔案搜尋與工具，不使用本插件 |
| B | 現有 v2.0.1 |
| C | 候選新版功能，逐模組開啟 |

固定模型版本、任務輸入、可用資料、權限與資源上限。先比較相同預算的品質，再比較達成相同品質的成本；不能只因 C 提供更多 token 或更強模型就把差異歸功插件。

初始至少 60 個任務：MD／技能治理、知識與專業實作、靜態／動態視覺各 20 個。開發與盲測各半，加入中文、中英混合、版本衝突、無正確答案與惡意來源文字。歷史資料有助建集，但測試答案不得混入可檢索庫。

每個條件可重複 3 次觀察模型變異；同一題的重複不是三份獨立任務。以任務為統計單位、提供信賴區間與配對結果。小樣本不足以證明差異時擴充盲測集，不把微小分數差宣稱顯著。

評測流程以明確目標、資料集、指標與持續比較為核心，模型判斷須用人工樣本校準。[OpenAI Evaluation Best Practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)

### 主要指標與候選門檻

| 面向 | 指標 | 初始門檻／判準 |
|---|---|---|
| 範圍正確 | 跨專案洩漏、越權修改 | 專門測試集零失敗；任何失敗阻擋該功能上線 |
| 文件完整 | 有效唯一條款保留、引用可定位 | 已核准變更計畫覆蓋 100%，未解衝突不套用 |
| 檢索 | 有答案題的 Recall@10、Precision@6 | 先以 90%／80% 為候選目標，按人工標註校準 |
| 來源 | 引用確實支持命題的比例 | 目標至少 95%，重要限制與版本需正確 |
| 任務成果 | 達標率、返工次數、必要人工修正 | 預先定義最小實用改善，例如達標率＋10 個百分點；不是已證實提升 |
| 成本 | 每個成功任務總 tokens、費用、時間 | 一般任務力求不高於 B；較貴時須有足夠品質收益 |
| 無關載入 | 被交付但與任務無關的材料占比 | 相較 B 明顯降低，不能以漏掉有效材料達成 |
| UI | 四個核心任務完成率、誤操作、時間 | 不低於現有版；選取及刪除語意不得誤導 |
| 視覺 | 功能、布局、可讀性、動態與偏好 | 多維評分；不能用單一美觀分數通過 |
| 校準 | 自稱完成但證據不足的比例 | 必須下降；無證據不得標示獨立驗證 |

額外做消融比較：僅關鍵字、混合檢索、加 reranker、加提示詞編譯、加視覺配方。若某步增加成本但沒有實用改善，就移除或維持選用。不能讓「完整功能」成為不敢刪除無效功能的理由。

## 7. 效能基線與測試邊界

現有歷史紀錄在指定 Windows／Node 環境下，10,000 文件冷索引約 98.99 秒、暖掃描約 2.193 秒；50 筆清單 p95 約 20.65 ms，索引搜尋 p95 約 1.47 ms。這是既有紀錄，並非本次重新驗證；不包含新語意模型、影片或完整 AI 任務。

未來使用相同資料及機器建立可重跑基線。候選目標：

- 10k 文件的基本清單與已索引文字查詢 p95 ≤100 ms，不含外部模型與網路。
- 暖掃描不重新讀取未變更文件正文；單檔改變只更新受影響索引。
- 長時間語意分析與媒體處理有進度、取消、重啟恢復，不阻塞前景清單。
- 100k／1M 片段另量索引、查詢、記憶體、磁碟及更新成本，再決定引擎。
- 保持並擴充與變更風險相符的既有測試；不對每次唯讀、文案或低影響動作強制跑全套。

歷史 43 項 core／MCP 與 31 個瀏覽器流程通過只能支持當時功能回歸，不能作為 AI 理解能力提升的證據。

## 8. 分期、依賴與出場條件

| 階段 | 交付 | 依賴 | 出場條件 |
|---|---|---|---|
| P0a | 現況測試集、完整用量帳本、版本／範圍契約、候選截取與快取失效修正 | 現有架構 | 能重現 B，能辨識實際與估計用量，標題順序不再截掉高相關候選 |
| P0b | AI／UI 共用操作、交易修正、基本 UI／編輯 | P0a | 核心流程無資料丟失、選取與回饋一致 |
| P1a | 五原則審核、差異、路由拆分、移動／整合 | P0b | 條款覆蓋、引用、復原及語意例外測試通過 |
| P1b | TaskBrief、來源入庫、混合檢索、脈絡包 | P0a、資料模型 | 盲測相關性、來源與成本達標 |
| P1c | 政策式自主維護、生命週期、領域包 | P1a、P1b | 只在授權範圍執行，衝突不誤合併 |
| P2a | 圖片區域、靜態配方、實作與比較 | P1b、素材契約 | 指定環境可重現，功能／視覺評價可追溯 |
| P2b | 動態時間軸、關鍵影格、引擎適配 | P2a | 時序、效能與成本達標 |
| P3 | 較大規模、跨平台、其他宿主 | 前述穩定版本 | 量測顯示需求，逐宿主能力測試通過 |

UI 配色、元件與操作一致性納入 P0b；完整知識、視覺畫面隨模組交付，避免先做一套按鈕眾多卻無法工作的介面。

## 9. 風險與待決策事項

| 風險 | 處理方式 |
|---|---|
| 知識誤導、版本衝突 | 來源與適用條件硬檢查，衝突顯示，不確定時不宣稱可直接採用 |
| 自動整理造成資料損失 | 前提式授權、完整計畫、hash／revision、隔離與復原 |
| 功能增多反而消耗上下文 | 按需工具與資料、共用預算、消融評測 |
| 視覺自評偏誤 | 獨立證據、多維評價、人工校準及盲測 |
| 大規模效能不穩 | 增量索引、工作器、量測後再換引擎 |
| 依賴特定模型／宿主 | 能力協商、適配器、JSON／MD／媒體匯出 |
| 安裝更新影響使用者資料 | 程式與資料分離、有版本遷移及復原測試 |

後續真正需要決定的是預設自治等級、主要視覺目標平台、是否允許外部 embedding／模型服務，以及希望優先降低成本或提高品質。本次先採「本機資料優先、符合政策才自主修改、進階昂貴流程選用」的規劃，不要求現在確認，也不進行實作。
