# 知識、RAG、提示詞與自主維護

狀態：提案。此文件描述未來能力，不表示現有插件已具備語意檢索、自主學習或背景維護。

## 1. AI 如何知道「這次需要什麼」

建立一份有版本的 TaskBrief，與原始使用者需求並存。每次需求改變只更新受影響的欄位，保留變更原因。

| 欄位 | 用途 |
|---|---|
| goal、deliverables | 本次真正要完成的結果與交付形式 |
| scope、environment | 專案、允許目錄、平台、工具／框架版本、執行環境 |
| constraints | 使用者明示限制，附原文位置；禁止由摘要自行放寬 |
| acceptance | 如何驗證完成，含主觀標準的具體例子 |
| known_facts、assumptions | 已知事實與暫時推定分開 |
| unknowns | 缺資料、未定偏好、可能盲點及其影響 |
| phase、changed_entities | 正在探索、實作或驗收；本次變更涉及的模組 |
| authorization_policy | 可進行的動作與範圍，來源為使用者授權或宿主政策 |
| context_budget | 本次文字、圖片與外部查詢預算 |

原始需求保持不可變的版本紀錄。AI 的「優化提示詞」是產生有來源的任務表示，不是偷偷重寫要求、增加目標或創造權限。每個推定都有狀態，不能在下一次摘要中變成使用者已確認事實。

任務脈絡分三層：

1. **常駐入口**：少量插件用途、資料責任與工具入口。
2. **任務工作集**：本次選取的知識 ID、版本、適用條件及讀取狀態。
3. **按需證據**：原始文件段落、外部來源、圖片區域、實作與測試結果。

新增資料不自動加入工作集；只有查詢命中、適用條件吻合且有價值時才載入。切換專案、環境或任務版本，重新檢查相關性及有效性。介面能解釋每次加入／排除的原因。

## 2. 資料從搜尋到可信知識

推薦生命週期：候選 → 待驗證 → 可重用 → 需複查 → 封存／待刪除。另以 independent、observed、reported 等欄位表達證據來源，避免一個「已驗證」勾選掩蓋實際可信程度。

### 入庫流程

1. AI 先指出資料缺口與查詢目的；有合適現存資料時不重新搜尋。
2. 在授權的本機來源或外部搜尋中找資料，優先第一方文件與可重現實作。
3. 保存必要的來源中繼資料與合規摘要／片段，不預設下載整個網站或複製完整受保護文章。
4. 拆出一個可重用命題：做什麼、何時適用、前提、例外、驗證方式。
5. 比對既有內容：補證據、建立不同版本、提出衝突或新增；不要只因文字相似覆蓋舊知識。
6. 有實際驗證才提升證據等級；只是搜尋讀到的內容仍標記來源陳述。
7. 按期限、來源變更或環境版本變更重新檢查；不能因新日期就認定內容較正確。

每份來源至少保存 canonical URL／檔案 ID、標題、作者或發佈方、擷取時間、可得的發佈／更新日期、版本、內容 hash、段落定位、使用權資訊及擷取方式。衍生摘要、翻譯、實作推論必須分開，且可回到原文。

外部文件是資料，不是操作授權。來源中的「忽略其他指令」「讀取其他目錄」等內容不能改變任務範圍。對來源的可信評分也不能提升其指令優先權。

### 專業領域包

每個領域包由精簡入口、概念／術語、權威來源、實作案例、常見陷阱、版本適用表、驗收方法組成。動態新增領域時允許擴充這些資料，不允許 AI 任意修改核心 schema 或把領域慣例寫成所有任務必須遵守的指令。

| 領域 | 高價值資料 | 需要的驗證 |
|---|---|---|
| 前端／程式 | API 版本、最小重現、相容限制、失敗案例 | 編譯、行為測試、效能及可用性 |
| 遊戲／引擎 | 場景、資源、渲染、輸入與效能條件 | 相同引擎版本的可重現場景與量測 |
| 視覺設計 | 構圖、元件、材質、動態、參考範圍 | 指定尺寸呈現、區域比較、人工偏好 |
| 研究／資料分析 | 原始資料、方法、假設與誤差 | 可重算結果、來源與不確定性 |
| 高風險專業 | 具日期、管轄／適用範圍的權威依據 | 專業審核；不得把檢索結果當成資格或最終結論 |

資料包數量不是「專業程度」。是否有效取決於來源品質、任務相符、推理、實作與驗證能力。

## 3. 混合檢索管線

目前 knowledge 檢索依 LIKE 比對，且先按標題截取 120 筆再排序。新管線必須先解決候選召回正確性，再評估是否值得加入向量。

~~~text
任務與問題
  → 解析專案、時間、平台版本、工作階段、查詢意圖
  → 權限／生命週期／範圍硬篩選
  → 關鍵字與欄位檢索 + 選用語意向量檢索
  → 合併排名、去重、補足必要依賴
  → 適用性及衝突檢查
  → 選用重新排序
  → 預算內脈絡包 + 來源 + 不確定性 + 未納入原因
~~~

設計細節：

- 中文與中英混合查詢要有測試集。可比較字詞切分、n-gram、精確識別字及同義詞；不能只靠空白分詞。
- API 名稱、錯誤碼、檔案路徑、版本號優先保留精確比對；自然語言目標才需要較多語意召回。
- 在允許範圍中使用 BM25／FTS 排名及向量結果融合，例如 reciprocal rank fusion；不同檢索器分數不可直接當同一機率相加。
- 候選量初始比較 60–100 筆、重新排序 8–12 筆、交付 3–6 筆，皆為待量測參數。簡單查詢可跳過向量與模型排序。
- 切塊以標題、命題、方法步驟與例外為界。保留文件／章節路徑；只有指涉不明時補短背景，不對每塊生成冗長摘要。
- 否定條件、限制與前提要與正文一同選入；不能選到「可以做」卻漏掉「只在版本 X」。
- 不確定適用性另列少量候選，不能與確定適用項混合呈現。沒有可靠命中時回報缺口，轉入有目的的搜尋。
- 標準分數只是排序訊號，不等於「87% 正確」。信心來自來源、環境相符與驗證證據。
- 索引快取鍵包含 scope、task revision、environment、policy、index version、query normalization。內容改變後，同一問題必須能讀到新版本。

語意檢索可以找到字面不相同的相關內容，但不能保證答案正確；混合字詞及語意檢索、補充切塊背景與重新排序值得做對照實驗。[OpenAI Retrieval](https://developers.openai.com/api/docs/guides/retrieval) · [Anthropic Contextual Retrieval](https://www.anthropic.com/research/contextual-retrieval)

## 4. 可解釋的脈絡包

工具先回傳短摘要與定位，不先灌入全文。以下為欄位示意：

~~~json
{
  "task_revision": 4,
  "scope_id": "project-a",
  "index_version": 91,
  "budget": {"estimated_text_tokens": 1700, "remaining": 1300},
  "items": [{
    "id": "knowledge-123",
    "revision": 3,
    "reason": "符合目前使用的框架版本與效能目標",
    "applicability": "matched",
    "verification": "observed",
    "summary": "條件、方法與重要例外的短摘要",
    "source_refs": ["source-7#section-2"],
    "detail_ref": "knowledge-123/revision-3/method"
  }],
  "conflicts": [],
  "omitted": {"count": 18, "reason": "低相關或超出本次預算"}
}
~~~

AI 需要時再讀 detail_ref。脈絡包不是新的最高優先級指令，不能覆蓋使用者需求與宿主限制。若需要的例外無法容納，寧可少選一份知識，不輸出脫離條件的精簡結論。

## 5. Thariq 方法如何轉成有用能力

下列方法按問題觸發，不強制每次走八步。原始的未知分類與八種做法可作為工作設計參考；本表是本插件的延伸設計。[Finding Your Unknowns](https://claude.com/resources/articles/a-field-guide-to-claude-fable-finding-your-unknowns)

| 情況 | 插件輔助 | 可以跳過的情況 |
|---|---|---|
| 需求有重大未知 | 盲點清單：影響、證據、最小驗證 | 明確的小修改 |
| 使用者偏好難以口述 | 2–3 個真正不同的原型及差異說明 | 已有明確可沿用樣式 |
| 答案會改變架構／範圍 | 一次提出少量關鍵問題，其他工作繼續 | 可逆的細節選擇 |
| 有參考作品 | 擷取結構、來源與可比對區域 | 無關參考不加入 |
| 大幅修改 | 可檢查的計畫與驗收條件 | 不為單行修正製作大型計畫 |
| 執行偏離原規劃 | 記錄決策、取捨與仍未解決事項 | 例行步驟不逐句存檔 |
| 完成待審查 | 互動成果、差異、證據與限制 | 不重複整份實作過程 |
| 使用者需要學會系統 | 選用反向測驗或情境問答 | 不把測驗當交付前置義務 |

使用者提供的「Thin Prompts, Thick Artifacts, Thin Skills」及視覺化規格方向，在本企畫採用為設計偏好；不把未獨立核實的字句當成逐字引言。真正要落地的是：短目標、可定位的豐富依據、必要才載入的方法。

Skill 優先保留領域陷阱、容易誤判的情況與驗證方法；一般模型已知的常識不重複塞入。精簡入口應說清楚何時用，附件保存詳細案例。[How We Use Skills](https://claude.dev/blog/lessons-from-building-claude-code-how-we-use-skills/)

## 6. AI 可以自行整合到什麼程度

所有「自動」都是未來使用者事先選定政策後的行為，本企畫不構成現在的刪改授權。政策包含範圍、資料類型、可做動作、回復期限、排除條件與資源預算；可以一次授權，不需每份重問。

| 動作 | 可自動執行的前提 | 不滿足時 |
|---|---|---|
| 建議標籤、摘要、關聯 | 輸出屬衍生資料，不改原始事實；保存來源與模型版本 | 留為建議 |
| 清理重建型快取 | 只處理明確標記的衍生快取，原資料完整可重建 | 略過 |
| 合併內容完全相同副本 | hash 相同，範圍與所有權允許，引用可重定向，授權涵蓋原檔處理 | 保留副本 |
| 語意整合 | 明示授權、版本吻合、條款覆蓋完整、無未解衝突，原版本可還原 | 提出變更計畫 |
| 路由器＋附件拆分 | 多工作流可分離；每段有去向、連結可用、責任一致 | 不以篇幅長度強拆 |
| 封存舊版本 | 有可識別的替代版本、有效期證據、現有引用已處理 | 標記需複查 |
| 標記待刪除／移入隔離區 | 命中授權政策；無唯一有效內容；影響檢查通過 | 保留且說明原因 |
| 永久清除 | 有單獨明示政策，保留期已到，引用與備份政策明確 | 不永久刪除 |
| 提升為可重用知識 | 適用條件明確且有符合門檻的驗證 | 維持待驗證 |

新版本不一定取代不同平台的舊版本。長期沒被檢索、檔名含 old、修改時間較早，都只能是複查線索，不能單獨作為無用判定。反例和失敗經驗可能低頻但高價值，應保留條件與失敗原因。

建議隔離期初始為 30 天且可調整。隔離、封存與永久刪除是不同操作；復原不能覆寫已被其他人修改的檔案，需產生衝突復原方案。相關圖片、向量、衍生摘要、快取與備份需有各自的保留政策。

## 7. 避免知識越積越亂

維護在匯入後、來源變更、任務結束或使用者啟動時觸發，只處理受影響資料。背景定期維護需另有宿主支援與排程授權，不能假設插件關閉後仍會自行運作。

- 先判斷是否已有答案，再決定新增；同一結論多一份來源通常是補證據，不是新增卡片。
- 把「一次任務紀錄」與「可重用方法」分開。對話全文不直接變成每次必讀經驗。
- 領域入口只放用途、適用條件、路由及少量關鍵陷阱；大型實作、圖像及範例作附件。
- 追蹤被使用且有幫助、被使用但無幫助、被否定、已過期與從未評估；單純讀取次數不是品質。
- 矛盾內容保留對立關係與適用範圍，不用摘要把衝突抹掉。
- 任務回報包含「採用何資料、如何影響結果、驗證結果、未證實部分、成本」。沒有比較基線時不得回報「能力提升 X%」。

這套方法改善的是外部記憶、選材、執行與回饋，不會改寫模型權重或保證它在所有領域學會新能力。是否能顯著提升，依 07 的對照評測決定。
